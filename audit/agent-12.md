### tests/test_audit4/c16_hex_panel_selection_dispatch/test_selection_dispatch.py:543-589 - TestCopyAsClipboardError
- Violation(s): Mock-the-thing-under-test, Weak-assertion-on-rich-output
- Why it is not a real gate: The tests use `patch("intellicrack.ui.panels.hex_editor.panel.QApplication")` and `patch("intellicrack.ui.panels.hex_editor.panel.show_warning", side_effect=_record_warning)` to mock the very clipboard and warning system under test. This violates the "no mocks for the operation under test" rule. The assertions only check that `show_warning` was called (via `len(warning_calls)`) rather than verifying the actual warning content, widget state, or user-visible behavior. Breaking the `_do_copy_as` production code to not call `show_warning` would still pass these tests.
- Severity: High
- Fix recommendation: Remove the `patch` calls and use real Qt clipboard operations. Build a fixture that provides a real `QApplication.clipboard()` instance or an actual system clipboard. Assert on the actual warning dialog's visible text, title, and user-dismissible behavior. For the "clipboard unavailable" test, set up a scenario where the real clipboard legitimately returns `None` or fails (if possible cross-platform) rather than mocking it.

### tests/test_hexcore_e2e/test_bridge_alignment_color.py:50-66 - test_snap_to_alignment_512
- Violation(s): Weak-assertion-on-rich-output, Cannot-fail
- Why it is not a real gate: The test asserts only `result == 1024`, which is a single numeric comparison. If the alignment-snapping logic were broken to return the floor instead of the rounded/nearest boundary, or if it ignored the alignment parameter entirely, the assertion could still pass if the bridge happened to return 1024 by chance. The test does not verify the algorithm's correctness over multiple test cases, boundary conditions, or the actual snapping behavior. There is no assertion that 1024 is indeed the nearest boundary to 1000 for 512-byte alignment.
- Severity: Medium
- Fix recommendation: Add multiple parametrized test cases covering various alignment factors and cursor positions that exercise different snapping directions (up vs. down). Assert not only the result but also validate that the result is mathematically the nearest boundary. Test edge cases: cursor at exact boundary (should be unchanged), alignment of 1, very large alignments, and positions where floor and ceil are equidistant.

### tests/test_hexcore_e2e/test_bridge_display_modes_complete.py:46-53 - test_set_hex16_be_returns_true
- Violation(s): Smoke-test-as-gate, Weak-assertion-on-rich-output
- Why it is not a real gate: The test asserts only that `set_display_mode("hex16_be")` returns `True`. This is a bare boolean check that does not verify the display mode was actually changed, that the bridge's internal state reflects the mode, or that subsequent reads return the set value. The test name suggests it validates the function, but only checks the return type and value, not the actual effect on the bridge.
- Severity: Medium
- Fix recommendation: For each mode-set test, immediately follow with `get_display_mode()` and assert that it returns the same mode that was set. Also verify that the bridge's internal display configuration actually changed (inspect bridge state or re-query the mode from a fresh connection). Test that setting an invalid mode raises an exception or returns False.

### tests/test_hexcore_e2e/test_bridge_yara_deep.py:303-312 - test_nonexistent_yar_file_raises_or_returns_error
- Violation(s): Cannot-fail, Weak-assertion-on-rich-output
- Why it is not a real gate: The test asserts `pytest.raises((FileNotFoundError, RuntimeError, Exception))` — a catch-all for any exception. This is so broad that it provides no guarantee of the specific error condition. If the bridge silently returns an empty list or crashes with an `IndexError`, the test still passes. The test does not verify that the error message mentions the missing file path, that the bridge logs the failure, or that the exception chain is informative.
- Severity: Low
- Fix recommendation: Narrow the exception tuple to the specific exceptions the production code is documented to raise (e.g., only `FileNotFoundError`). Assert on the exception message to confirm it references the nonexistent file path. Verify that the exception is not swallowed upstream and is propagated faithfully to the caller.

### tests/test_providers/test_http_status_helper.py:62-71 - test_returns_none_for_unmatched_status
- Violation(s): Weak-assertion-on-rich-output
- Why it is not a real gate: The test asserts only `result is None` without verifying that the exception was NOT raised and that the helper correctly fell through to the caller. If the helper were modified to always raise a ProviderError regardless of the status code, this test would still pass (because the exception would propagate and fail the test, but not in a clear way). The test should also verify that no side effects occur (no logging, no state changes).
- Severity: Low
- Fix recommendation: Assert that `result is None` AND capture any logs or side effects to confirm the helper silently returned without side effects. Verify that the originating exception is accessible as the cause chain for debugging. Add a parametrized test for multiple non-matching status codes (e.g., 500, 502, 504) to ensure broad coverage of the "no match" case.

### tests/test_bridges/test_win32_types.py:196-211 - test_value_matches_expected_bit_pattern
- Violation(s): Tautological, Cannot-fail
- Why it is not a real gate: The test asserts `expected == INVALID_HANDLE_VALUE` where `expected = ctypes.wintypes.HANDLE(-1).value` — this is re-deriving the expected value using the same mechanism as the production code, making it a tautology. If the production code were broken, this test would fail only if the break affected both the test's derivation AND the constant identically. The assertion `assert INVALID_HANDLE_VALUE == 0xFFFFFFFFFFFFFFFF` hardcoded after is correct, but the initial `expected` derivation defeats the purpose.
- Severity: Low
- Fix recommendation: Use a known-correct constant (from Windows documentation: -1 cast to HANDLE on the target platform) or a trusted external oracle, not the production code's own mechanism. Assert against the platform-specific bit patterns (0xFFFFFFFFFFFFFFFF for 64-bit, 0xFFFFFFFF for 32-bit) directly without re-deriving.

### tests/test_ui/test_process_panel.py:352-355 - test_tool_definition_count
- Violation(s): Smoke-test-as-gate
- Why it is not a real gate: The test asserts only that the tool definition has exactly 54 functions, without verifying that those functions are actually callable, have correct signatures, or are correctly bound to bridge methods. A count assertion alone does not guarantee that the bridge is functional or correctly wired. Adding a dummy stub function would satisfy this test without fixing any real issues.
- Severity: Low
- Fix recommendation: Instead of a bare count assertion, iterate through each function and verify: (1) it has a non-empty name and description, (2) the name correctly maps to a callable bridge method (via `hasattr` and `callable`), (3) the method signature matches the tool definition's parameters, and (4) at least one function is actually invoked to confirm it works end-to-end.

### tests/test_ui/test_process_panel.py:363-373 - test_function_names_map_to_methods
- Violation(s): Weak-assertion-on-rich-output
- Why it is not a real gate: The test iterates through functions and asserts `hasattr(b, method_name)` but does not verify that the method is callable, has the correct signature, or actually works when invoked. A method attribute could be None, a property that raises, or a method with completely different parameters. The test does not exercise the method or verify its behavior.
- Severity: Low
- Fix recommendation: For each function, verify not only `hasattr` but also `callable(getattr(b, method_name))`. If possible, invoke a simple method (e.g., one with no arguments or with safe defaults) and assert it returns a result consistent with the tool definition. Test error paths by attempting to call with invalid arguments and verifying the bridge raises the documented exception type.

### tests/test_ui/test_realcov_15_resource_url_dispatch.py:119-143 - test_resource_button_click_routes_real_url_through_qt
- Violation(s): Weak-assertion-on-rich-output

It asserts `url_recorder.urls[-1] == expected[label]`, but does not verify that the button itself is visible, enabled, or correctly labeled in the UI. Verify that clicking the button actually fires the underlying signal/slot chain (not just the handler). Optionally, for real URLs, validate that the URL is well-formed and the endpoint responds (at least a HEAD request to the domain).
