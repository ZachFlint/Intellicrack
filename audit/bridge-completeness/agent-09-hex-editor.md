**Bridge**: `src/intellicrack/bridges/hex_editor.py` (9261 lines, 120 public async methods)
**Panels**: `src/intellicrack/ui/panels/hex_editor_panel.py` (re-export shim → `ui/panels/hex_editor/` package, 24 files, 13146 lines), `src/intellicrack/ui/panels/hex_editor_widget.py` (2131 lines, the interactive grid widget), `src/intellicrack/ui/panels/hxd_panel.py` (separate embedded-process panel, out of scope for bridge wiring — see note at bottom)

## Architecture note (read first)

The interactive panel (`ui/panels/hex_editor/panel.py:720`) opens files via `self.document = hexcore.HexDocument.open(path)` — a native Rust document object — and publishes it into a **shared** `HexDocumentState` holder (`bridges/hex_state.py`) via `state_holder.set_document(...)` (`panel.py:747-748`). The async bridge (`hex_editor.py`) reads/writes through this same shared state holder (`self.document` property backed by `state_holder`). Consequently most GUI mixins call methods **directly on `self.document`** (the native object) rather than routing through `run_bridge_coroutine`. This is legitimate wiring — GUI and bridge observe/mutate the identical underlying document — and is scored **OK**, not DEAD-CONTROL, throughout this report. Only `run_bridge_coroutine`/`run_bridge_coroutine_logged` calls to `self._bridge` are noted separately where present (used for cross-process-safe or format-normalizing operations, e.g. patch export/import, PE section/import/export parsing, `encode_text`, `compare_files`).

Layer 1 (bridge) and Layer 2 (tool-definition/dispatch) were verified programmatically: `grep -oP 'name="hex_editor\.\K[a-zA-Z_0-9]+' hex_editor.py` yields **112** registered `ToolFunction` entries inside the single `tool_definition` property (`hex_editor.py:492-...`); `grep -oP '^\s+async def \K[a-zA-Z_0-9]+' hex_editor.py` yields **120** async methods. The 8-method delta is entirely private helpers (`_detect_elf_va_mappings`, `_detect_macho_va_mappings`, `_detect_pe_va_mappings`, `_resolve_patch_source`, `_sandbox_create_and_copy`) and lifecycle methods (`initialize`, `is_available`, `shutdown`) that are correctly excluded from tool-calling. **Every public async method has a registered ToolFunction and is dispatchable** via `core/tools.py:587-588` (`getattr(bridge, function_name.split(".", 1)[-1])`). Layer 1/2 are therefore OK for 100% of the native surface unless individually noted STUB below (none found — every method reviewed performs real work against the native document / Rust FFI / PE parsers / YARA / hashlib / capstone, with real error handling).

Given L1+L2 are uniformly OK, the coverage matrix below focuses columns on **GUI reachability** (L3), since that is where the real gaps are.

## Prioritized gap list

1. **Search & Replace (highest impact)** — `replace_bytes` (`hex_editor.py:5329`) is fully implemented and registered but the GUI's Search tab (`ui/panels/hex_editor/search.py`) has Hex/Text/Regex/Numeric *search* modes with zero *replace* affordance (no "Replace", "Replace All", or "Replace Selected" button anywhere in the mixin or `panel.py`). This is a core professional-hex-editor feature and the single biggest usability gap. **Fix location**: add replace controls to `search.py` (new `_on_replace`/`_on_replace_all` handlers calling `document.replace_bytes` or `run_bridge_coroutine(bridge.replace_bytes(...))`), wired from a new UI row in `panel.py`'s search-tab construction.

2. **Annotated HTML/PDF export** — both `export_annotated_html` (`hex_editor.py:8342`) and `export_annotated_pdf` (`hex_editor.py:8413`, backed by a real `fpdf2`-based `_FPDFProtocol` implementation, not a stub) are complete, reporting-grade features with no GUI trigger at all. High value for analysts producing deliverables. **Fix location**: add an "Export Report..." action (menu or toolbar) in `panel.py` that calls `run_bridge_coroutine(bridge.export_annotated_html(...))` / `export_annotated_pdf(...)` and writes the result via `QFileDialog.getSaveFileName`.

3. **Signature scanning (DIE / ClamAV / custom)** — three fully implemented scan methods (`hex_editor.py:8977-9199`) with real signature-database parsing have no GUI surface anywhere. `yara.py` has the pattern (rule-file picker + scan button + results tree) that could be replicated. **Fix location**: extend `ui/panels/hex_editor/yara.py` (or a new `signatures.py` mixin) with DB-path pickers and scan buttons calling `bridge.scan_die_signatures`/`scan_clamav_signatures`/`scan_custom_signatures`, mirroring the existing YARA UI pattern at `yara.py:82-100`.

4. **VA mapping / offset↔VA conversion** — `set_va_base`, `list_va_mappings`, `auto_detect_va_mappings`, `remove_va_mapping`, `file_offset_to_va`, `va_to_file_offset` (`hex_editor.py:8187-8342`) are all real (including auto-detection helpers `_detect_pe_va_mappings`/`_detect_elf_va_mappings`/`_detect_macho_va_mappings`) but have no GUI. This matters for process-memory work since `process_memory.py` already opens live memory regions — VA↔file-offset conversion is the natural companion feature. **Fix location**: add a VA-mapping panel to `ui/panels/hex_editor/process_memory.py` (list/add/remove mapping rows + a goto-by-VA input calling `va_to_file_offset` then the existing `goto_offset` path).

5. **Chunk size / memory budget controls** — `set_chunk_size`, `get_memory_usage`, `set_memory_budget` (`hex_editor.py:8514-8593`) are real large-file tuning knobs with no GUI exposure. Lower priority (power-user/performance tuning, not core editing), but worth a settings-dialog entry. **Fix location**: add to a preferences/settings dialog if one exists, or a small "Performance" section in `panel.py`'s toolbar overflow.

6. **Sandbox integration uses the wrong bridge (functional regression risk)** — `sandbox.py:154-249` (`_on_save_to_sandbox`/`_on_test_in_sandbox`) calls a generic `SandboxBridge.copy_to`/`SandboxBridge.execute` directly instead of the hex-editor-specific `save_to_sandbox`/`test_in_sandbox` (`hex_editor.py:5024,5117`). The bridge methods are strictly more capable: they auto-provision a sandbox instance via `sandbox_bridge.create()`, auto-destroy it on failure to avoid orphaned VMs/containers (hex_editor.py:5089-5107), and transparently write a temp file when the open document is unsaved/in-memory (hex_editor.py:5063-5071). The GUI path has none of this — it requires the user to already have a running instance selected in a combo box and offers no cleanup-on-failure. This is higher priority than a typical "duplicate implementation" finding because the GUI path is not just divergent but *functionally worse* (can leak sandbox instances, cannot save unsaved documents). **Fix location**: `ui/panels/hex_editor/sandbox.py:154-249` — replace the direct `SandboxBridge.copy_to`/`.execute` calls with `run_bridge_coroutine_logged(bridge.save_to_sandbox(...))` / `bridge.test_in_sandbox(...)` against the hex-editor bridge, or explain in a comment why the generic path was chosen over the safer hex-editor-specific one if that was intentional.

7. **Duplicate-implementation orphans (bridge/GUI drift risk)** — nine additional bridge methods have a fully working GUI equivalent that reimplements the same logic independently instead of calling the bridge method:
   - `base_convert` (`hex_editor.py:6959`) vs. `calculator.py:100-161` (`struct`-based local conversion)
   - `generate_structure_bookmarks` (`hex_editor.py:7196`) vs. `templates.py:505-600` (manual PE/ELF header walk + `document.add_bookmark`)
   - `auto_detect_pattern` (`hex_editor.py:7429`) vs. `sections.py:444-472` (`PatternRegistryCls.match_file()` direct call)
   - `scan_die_signatures`/`scan_clamav_signatures`/`scan_custom_signatures` (`hex_editor.py:8977-9199`) vs. `signatures.py` local `_scan_die`/`_scan_clamav`/`_scan_custom` functions
   - `toggle_bit` (`hex_editor.py:5834`) vs. the get_bit+set_bit checkbox pattern in `data_inspector.py`
   - `list_process_regions` (`hex_editor.py:8094`) vs. `process_memory.py:170` calling `hexcore.HexDocument.list_process_memory_regions` directly
   - `run_python_script` (`hex_editor.py:9199`, deliberately hard-disabled for security) vs. `scripting.py`'s independent sandboxed `execute_script` (scripting.py:1297-1347) — the only working path, since the bridge method is intentionally a permanent no-op

   None of these are user-facing gaps today (the GUI feature works, in most cases via a genuinely separate code path), but each pair is logic duplicated in two places that can silently diverge on bug fixes, and each bridge method is unreachable except via direct AI/orchestration tool-calls — meaning an AI agent asking the bridge to "auto-detect a pattern" or "generate structure bookmarks" gets a different (and non-tested-against-the-GUI) code path than what the user sees when they click the equivalent button. **Fix location**: for each pair, either (a) have the GUI call the bridge/document method instead of reimplementing, or (b) have the bridge method delegate to the same shared helper function the GUI already uses, so there is a single source of truth. Prioritize `scan_die_signatures`/`scan_clamav_signatures`/`scan_custom_signatures` and `generate_structure_bookmarks` since those involve nontrivial parsing logic most likely to drift; `base_convert` and `toggle_bit` are simple enough that drift risk is low. `run_python_script` is intentionally excluded from consolidation — the bridge's in-process sandbox was permanently disabled after an RCE finding, so `scripting.py`'s separate implementation should be audited on its own merits rather than pointed at the disabled bridge method.

`ui/panels/hxd_panel.py` embeds the third-party HxD executable as a separate top-level process (via `QProcess` + Win32 window reparenting) — it does not call the `hex_editor.py` bridge at all and has no `_td`/dispatch relationship to it. This is a legitimate, independent integration (external-tool embedding, not the native hex-editor bridge) and is excluded from the coverage matrix above; it was reviewed only to confirm it is real, working code (registry probing at `hxd_panel.py:54-77`, process launch/embed at `hxd_panel.py:254-357`, all real — no stubs).
