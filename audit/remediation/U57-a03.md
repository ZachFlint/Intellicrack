## Summary

The original file mocked the thing under test: `_AddCallRecorder` /
`_RemoveCallRecorder` stood in for the real `HexEditorBridge`, and
`_FakeHexWidget` / `_FakeHighlightRule` stood in for the real widget and rule.
Tests only asserted "the recorder was called" and never proved the
bridge -> state-holder -> widget confirmation path actually updates the real
widget.

Every test was rewritten to drive the genuine `HighlightingMixin` against a
**real** `HexEditorWidget`, a **real** `QListWidget`, a **real**
`HexEditorBridge`, and a **real** `HexDocumentState`, wired exactly the way
`HexEditorPanel.set_state_holder` wires them. The bridge coroutines are awaited
directly so the state-holder notification (fired synchronously inside the
coroutine body) drives the mixin's widget mutation on the test thread
(deterministic, Qt-safe).

### Production bug found and fixed (legitimately required by the real-data rewrite)

`HighlightingMixin._apply_bridge_highlight_rule_removed` called
`self._hex_widget.remove_highlight_rule(row)` passing an **int row index**, but
the real `HexEditorWidget.remove_highlight_rule(rule_id: str)` matches by
**rule_id string**. The fake widget removed by index, masking the defect: against
the real widget the rule was never removed from the widget store. Fixed to pass
`rule_id`. Falsifiability verified: reverting to `remove_fn(row)` turns
`test_remove_rule_clears_widget_list_and_state` red; restoring it returns green.
File changed: `src/intellicrack/ui/panels/hex_editor/highlighting.py` (one line).
