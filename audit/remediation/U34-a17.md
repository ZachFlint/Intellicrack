# U34-a17 Remediation — tests/test_hexcore_e2e/test_bridge_sandbox.py

Unit covers the precondition-ordering guards of `HexEditorBridge.save_to_sandbox`
and `test_in_sandbox`, the cross-bridge `ToolName.SANDBOX` lookup against a real
`ToolRegistry`, and verbatim forwarding of `sandbox_type` into the real
`SandboxBridge`. All four audited findings from agent-17.md are addressed in
place. No mocks: every test drives the real bridge, a real `ToolRegistry`, and a
real `SandboxBridge` through to the genuine `RuntimeError`/`ToolError` each layer
raises.

## Falsifiability notes

- Each guard test asserts the **exact** message via `==` (not `match=` substring)
  and `type(exc) is RuntimeError`, so a `RuntimeError` from a different code path
  or with a different message fails the gate.
- Each guard test pairs the negative case with a **boundary** assertion driving
  the same operation past the guard into the real `SandboxBridge`, which raises
  `ToolError("Invalid sandbox_type: '<value>'")`. Production (`sandbox_bridge.py`)
  builds this message with `{sandbox_type!r}` and validates against the
  case-sensitive `frozenset({"windows", "qemu"})`, so `"Windows"` (capital) is a
  genuine reject — proving exact, non-coercing forwarding.
- If the production `sandbox_bridge is None` guard were removed, the empty-registry
  call would reach `getattr(None, "create", None)` → non-callable →
  `TypeError("sandbox bridge does not support create")`, which the
  `pytest.raises(RuntimeError)` + exact `==` assertion would flag red.
