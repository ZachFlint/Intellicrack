# Remediation U34 - agent-17.md

Unit file (owned whole): `tests/test_hexcore_e2e/test_bridge_sandbox.py`

## Root cause shared by all findings

The original tests drove `HexEditorBridge.save_to_sandbox` / `test_in_sandbox`
through `_MinimalRegistry` - a hand-written fake double of `ToolRegistry` that
returned `None` for every bridge lookup - and asserted only loose substring
matches (`match="tool registry"`, `match="sandbox bridge not available"`). That
made the tests non-gating: a `RuntimeError` from any code path containing those
words passed, and the real cross-bridge `ToolName.SANDBOX` lookup and argument
forwarding were never exercised.

The rewrite removes the fake registry entirely and uses two REAL fixtures:
`empty_registry` (a real `ToolRegistry` with no bridges) and `sandbox_registry`
(a real `ToolRegistry` holding a real `SandboxBridge` registered via
`register_bridge`). Every assertion now compares the FULL exact error string,
and the cross-bridge path is proven end to end: an empty real registry yields
`RuntimeError("sandbox bridge not available")`, while a populated real registry
forwards an invalid `sandbox_type` all the way into the real
`SandboxBridge.create` / `run_binary` up-front validation, which raises
`ToolError("Invalid sandbox_type: '<value>'")` - the value echoed back proves
verbatim forwarding. The independent oracle is `SandboxBridge`'s own documented
validation (`_VALID_SANDBOX_TYPES = {"windows", "qemu"}`), a different component
from the hex bridge under test.
