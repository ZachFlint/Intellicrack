# Intellicrack GUI Audit — 2026-07-01

**Scope:** Exhaustive read-only audit of the PyQt6 GUI (~75,300 lines across ~90 files under `src/intellicrack/ui/`).
**Method:** Six parallel per-cluster audits (app shell/docking, hex editor, frida/x64dbg/process, ghidra/cutter, dialogs/config, log viewer/theming/resources). Every finding verified against surrounding code.
**Result:** 58 findings. No code was modified.

## Systemic patterns

Most serious findings collapse into three recurring root causes — fix these at the pattern level:

1. **Cross-thread UI mutation / `QTimer.singleShot` from non-GUI threads** → intermittent hard crashes (`widgets cannot be accessed from a different thread`). Correct pattern: emit a `pyqtSignal` from the callback thread and connect it to a GUI-thread slot (Qt auto-queues), as `FridaPanel._frida_message_received` already does.
2. **Hardcoded dark-theme colors** → text invisible/faded in the light theme; widgets never subscribe to `ThemeManager.theme_changed`.
3. **Blocking bridge calls on the UI thread** → periodic multi-second freezes; use the async `run_bridge_coroutine_logged` worker path with timeouts.

Severity legend: **CRITICAL/HIGH** = crash or data-integrity; **MEDIUM** = wrong behavior / freeze; **LOW** = cosmetic, edge-case, i18n, minor leak.

## CRITICAL / HIGH — crashes & data integrity

### H1 — Cross-thread UI mutation in `_on_bridge_analysis_received`
- **File:** `src/intellicrack/ui/app.py:1133-1135`
- **Severity:** HIGH
- The method's own docstring states it must marshal to the Qt main thread via signal emission, then does two direct UI-mutating calls (`tool_panel.clear_analysis_tab`, `tool_panel.display_analysis_result`) on the worker thread *before* the safe `bridge_analysis_received.emit`. Registered via `set_bridge_analysis_callback`/`configure_hooks` (lines 1048-1052); fires from the `AsyncWorker` thread running `orchestrator.process_user_input`.
- **Failure:** When an AI-driven analysis completes, the analysis tab is updated from a worker thread — intermittently corrupts rendering or hard-crashes (Qt aborts on cross-thread widget access), worst under repeated analyses.

### H2 — x64dbg debug-event auto-refresh scheduled via `QTimer.singleShot` from the bridge event thread
- **File:** `src/intellicrack/ui/panels/x64dbg_panel.py:1154-1165` (`_on_debug_event`)
- **Severity:** HIGH
- `QTimer.singleShot(0, ...)` binds to the *calling* thread. The bridge event thread has no Qt event loop, so either the timer never fires (breakpoint/watchpoint/step auto-refresh silently never happens) or, if that thread spins a loop, `_refresh_state()` mutates `QTableWidget`/`QPlainTextEdit` off the GUI thread → crash. Correct pattern is a `pyqtSignal` (as `frida_panel.py:111,120` does).
- **Failure:** Attach x64dbg, hit a breakpoint — register/stack/disasm views never update, or the app crashes fatally.

### H3 — Hex editor background workers not stopped on panel teardown
- **File:** `src/intellicrack/ui/panels/hex_editor/panel.py:1308-1330` (`_cleanup`)
- **Severity:** HIGH
- `_cleanup` interrupts/waits only `_statistics_worker`, `_search_worker`, `_numeric_search_worker`. Four other `GenericCallableWorker` QThreads — created **without a Qt parent**, held only by a Python attribute — are never stopped: `_diff_worker` (`comparison.py:189`), `_strings_worker` (`sections.py:333`), `_sig_worker` (`signatures.py:613`), `_script_worker` (`scripting.py:1342`).
- **Failure:** Run a signature scan / string extraction / diff / long script on a large file, then close the panel or app before it finishes → `QThread: Destroyed while thread is still running` hard abort. A mid-flight diff also strands its `NamedTemporaryFile` (`_cleanup_diff_temp` only runs from diff completion handlers).

### H4 — Log rows invisible in light theme
- **File:** `src/intellicrack/ui/log_viewer/_model.py:44-56, 301-304`
- **Severity:** HIGH
- `_LEVEL_COLORS` is a hardcoded dark palette: `INFO=QColor(220,220,220)` (near-white), `DEBUG=QColor(120,120,120)`. Only WARNING/ERROR/CRITICAL get a `BackgroundRole` override, so INFO/DEBUG inherit the themed background. In the light theme (`theme_manager.LIGHT_THEME_FALLBACK` → `QTableView{background:#ffffff}`) near-white INFO text renders white-on-white. Model never subscribes to `ThemeManager.theme_changed`.
- **Failure:** Switch to light theme — most log lines (INFO is default) become unreadable.

## MEDIUM — functional bugs

### Thread-safety / UI freezes

#### M1 — StackViewerPanel runs blocking bridge coroutines on the UI thread every 500 ms
- **File:** `src/intellicrack/ui/panels/stack_viewer.py:165-196, 242-272` (`get_stack_frames` → blocking `run_bridge_coroutine`), driven by `refresh()` (585) on a 500 ms timer (542).
- Unlike sibling panels (which use async `run_bridge_coroutine_logged`), these call the synchronous variant on the GUI-thread timer, blocking the event loop for the full IPC round-trip.
- **Failure:** Enable "Auto" while the debugger backend is slow → UI freezes in 500 ms stutters.

#### M2 — 30 s status timer and Refresh Models block the UI thread with no timeout
- **File:** `src/intellicrack/ui/app.py:933` (`_refresh_system_status` → `run_bridge_coroutine(fetch_status())`), `app.py:2192` (`discover_all()`); `run_bridge_coroutine` blocks on `future.result()` with no timeout (`async_bridge.py:393`).
- **Failure:** Every 30 s the UI freezes for the status fetch duration; if the orchestrator or network discovery hangs, the GUI freezes indefinitely with no recovery.

#### M3 — VNC framebuffer QImage mutated on bridge thread, read on GUI thread
- **File:** `src/intellicrack/ui/panels/vnc_widget.py` — writes in `apply_raw_rect` (1033-1037) on the bridge loop; `paintEvent` reads `client.framebuffer.scaled(...)` (1911-1920) on the GUI thread.
- The `asyncio.Lock` (`_fb_lock`) only serializes bridge-loop coroutines; it does not guard `paintEvent`. `QImage` is not thread-safe for concurrent read/write.
- **Failure:** Active session with continuous updates — `scaled()` reads half-written scanlines (torn frames) or, on reallocation, freed buffer memory (intermittent crash).

#### M4 — Synchronous VNC connect blocks the GUI thread up to the connect timeout
- **File:** `src/intellicrack/ui/panels/vnc_widget.py:1803` (`_run_connect_and_start_pump` → `run_bridge_coroutine(client.connect(...))`), invoked from `SandboxPanel._connect_vnc_with_password` on the main thread.
- **Failure:** UI freezes up to `_DEFAULT_CONNECT_TIMEOUT` (10 s) if the VNC port is unreachable/slow.

#### M5 — Sandbox availability probe runs a blocking PowerShell subprocess on the GUI thread during dialog construction
- **File:** `src/intellicrack/ui/sandbox_config.py:379` (`_check_availability` in `__init__`) → `_run_sandbox_availability_check` runs `powershell ... Get-CimInstance` with `timeout=10` (518-533). `tools.py:1922-1923` constructs a throwaway `SandboxConfigDialog()` just to call `is_sandbox_available()`, firing this probe every time the Sandbox tab is added; the discarded dialog is never disposed.
- **Failure:** When `WindowsSandbox.exe` is absent, dialog construction (and adding the Sandbox tab) blocks the main thread up to 10 s.

### Wrong behavior / wrong data

#### M6 — Frida device combo always connects as "local"
- **File:** `src/intellicrack/ui/panels/frida_panel.py:1004-1032` (`_on_device_changed`) vs `1295-1314` (`_populate_device_combo`).
- Combo is filled with display strings (`"USB Device (usb)"`) and the real id in `userData`, but `_on_device_changed` branches only on `device_text.startswith("remote:")` / `== "usb"` and never reads `userData` → `device_type` stays `"local"` for every enumerated device.
- **Failure:** Select the USB device → bridge is told `connect_device("local", None)`.

#### M7 — Register table shows 64-bit names even for 32-bit targets
- **File:** `src/intellicrack/ui/panels/x64dbg_panel.py:2085-2097` (`_apply_registers`); constant `_GENERAL_REGS_64` at 80-98.
- `all_regs` is always `[*_GENERAL_REGS_64, _FLAG_REG, *_SEGMENT_REGS]` regardless of `self._is_64bit`. Value width adapts (`0x{value:08X}` when 32-bit) but names do not; `getattr(regs, "r8".."r15", 0)` yields bogus zero rows.
- **Failure:** Debug a 32-bit binary — table shows eight nonexistent `r8`–`r15` zero rows and mislabels `eax` as `rax`; never shows `eax`/`eip`.

#### M8 — Thread-selection combos reset on every auto-refresh
- **File:** `src/intellicrack/ui/panels/process_panel/threads_tab.py:99-109` (`update_thread_list`), invoked from `_refresh_threads._on_success` (416) on the 3 s auto-refresh timer.
- `combo.clear()` + repopulate on the Registers/Stack/Exceptions/Fibers/TLS combos resets the user's selection to index 0 every 3 s; subsequent `currentData()` reverts to the first thread.
- **Failure:** Pick TID 4000 in Registers; within 3 s it snaps back and Refresh/Write Registers targets the wrong thread.

#### M9 — Float numeric search broken on the native FFI path
- **File:** `src/intellicrack/ui/panels/hex_editor/search.py:258-278` (`execute_numeric_search`), dispatched from `_on_numeric_search` (725).
- `use_native = hasattr(document, "search_numeric")` is set regardless of type; native calls pass no float flag and coerce with `int()`. The correct float fallback (`_numeric_search_fallback`, `f`/`d` struct format) is only reached when the document lacks `search_numeric`.
- **Failure:** Type = "Float", search `1.5` → truncated to integer `1`, matches integer bit patterns not IEEE-754.

#### M10 — Text search/replace uses combo display text instead of the codec name
- **File:** `src/intellicrack/ui/panels/hex_editor/search.py:386` (`_on_search`), `825` (`_replace_encoding`).
- `encoding = enc_text.lower().replace("-", "")` uses `combo.currentText()` (the human label) instead of `currentData()` (the codec), unlike the correct `_on_encoding_changed`.
- **Failure:** With label `"ASCII (7-bit)"`, encoding becomes `"ascii (7bit)"` → `search_text_encoded` raises `LookupError` → text search silently fails.

#### M11 — Tool install path falls back to CWD when field is empty
- **File:** `src/intellicrack/ui/tool_config.py:1227-1230`.
- `install_path = Path(self._path_input.text().strip())` then `if not install_path:` — `Path("")` is `WindowsPath('.')`, always truthy, so the guard never fires. Should test the stripped string before wrapping.
- **Failure:** Clear the path field → downloaded ZIP extracts into the current working directory instead of `tools/<tool_id>`.

#### M12 — Restored "Auto-approve: ON" state not applied to orchestrator at startup
- **File:** `src/intellicrack/ui/app.py:862-877`.
- `setChecked(initial_auto_approve)` (871) is called before `toggled` is connected (877), so `_on_auto_approve_toggled` (which sets `ConfirmationLevel.NONE`) never fires during init.
- **Failure:** Toolbar shows "Auto-approve: ON" but destructive tool calls still prompt until the user toggles off and on.

#### M13 — Model selection silently lost on Refresh Models
- **File:** `src/intellicrack/ui/app.py:2187` vs `2214-2223`.
- `_on_refresh_models` calls `model_combo.clear()` before the worker starts; `_on_models_refresh_finished` reads `currentText().strip()` for restore — always `""`. The findText/setCurrentText restore block is dead code.
- **Failure:** Selected model discarded on every refresh even when still present.

### Graph / layout / parsing

#### M14 — CFG `fit_to_view` fits to a stale, oversized scene rect
- **File:** `src/intellicrack/ui/panels/graph_view.py:311-319` (`load_graph` clears but never `setSceneRect`), `525-529` (`fit_to_view` uses `scene.sceneRect()`); triggered from `cutter_panel.py:845-846`.
- Qt's implicit `sceneRect()` only grows; after a large CFG a small one fits to the union. Fix: `scene.setSceneRect(scene.itemsBoundingRect())` after `load_graph`.
- **Failure:** Large function then a 2-block function → small graph is a corner speck.

#### M15 — Ghidra CFG is loaded but never fit into view
- **File:** `src/intellicrack/ui/panels/ghidra_panel.py:2052-2054` (`_apply_cfg`).
- No `fit_to_view()`/`fitInView` after `scene.load_graph(...)` (Cutter does at `cutter_panel.py:846`), so the graph keeps the prior zoom/scroll transform. Compounds M14.
- **Failure:** Open the CFG tab — graph appears at prior zoom/offset (often empty space); user must manually pan/zoom.

#### M16 — Function tree Address/Size columns sort as strings
- **File:** `src/intellicrack/ui/panels/ghidra_panel.py:1837-1849` (sorting enabled 1284), `cutter_panel.py:641-653` (sorting enabled 239).
- Address stored as hex string, Size as decimal string; default lexicographic `QTreeWidgetItem` compare. No numeric sort key set.
- **Failure:** `0x9` sorts after `0x1000`; `"100" < "20"`.

#### M17 — Function filter issues a full bridge RPC on every keystroke
- **File:** `src/intellicrack/ui/panels/ghidra_panel.py:1269` + `1859-1865`; `cutter_panel.py:234` + `663-669`.
- `textChanged.connect(_on_filter_changed)` calls `_on_refresh_functions()` per character, no debounce.
- **Failure:** A 10-char filter fires 10 concurrent async queries that complete out of order; the tree can show results for an earlier partial string, plus backend flooding.

#### M18 — Block dialogs parse input outside try/except
- **File:** `src/intellicrack/ui/panels/hex_editor/transforms.py:851, 874, 895, 914` (`_on_block_fill`/`_copy`/`_move`/`_swap`); `get_values()` at 1047-1049, 1087-1090, 1128-1132 calls `int(text,0)` / `bytes.fromhex(...)`.
- Only the subsequent `document.*` call is wrapped; the parse is not.
- **Failure:** Enter `0xZZ` or `GG` and click OK → uncaught `ValueError` out of the Qt slot → PyQt6 default excepthook aborts the app.

#### M19 — Splash screen sized in physical pixels but treated as logical → 2× oversized on HiDPI
- **File:** `src/intellicrack/ui/dialogs/splash_screen.py:169-175`.
- `scaled_w = int(SPLASH_WIDTH * dpi_scale)` but the base pixmap's `devicePixelRatio` is never set, so `QSplashScreen` treats a 1200×800 pixmap as logical points. Paint code also multiplies by `dpi_scale`. Fix: `transparent_pixmap.setDevicePixelRatio(dpi_scale)`.
- **Failure:** Splash and its contents render ~2× oversized on a 2× display.

#### M20 — Offset addresses painted with the wrong (semi-transparent) color
- **File:** `src/intellicrack/ui/panels/hex_editor_widget.py:699-700`.
- Offsets drawn with `_colors["selection_bg"]` (in light theme `QColor(0,120,212,80)`, alpha 80) instead of the existing `"offset_text"` color (only used for the "No file loaded" placeholder at 651).
- **Failure:** Offset addresses render faded/hard to read in light theme; opaque blue instead of gray in dark theme.

#### M21 — EntropyMiniMap never receives data and is positioned outside the widget
- **File:** `src/intellicrack/ui/panels/hex_editor_widget.py:166` (`set_entropy_data` defined, never called), `512` (`_ensure_entropy_cache` computes but never pushes to `_minimap`), `1748-1758` (`_position_minimap` places it at `vbar_geom.right()+1` with no `setViewportMargins`).
- **Failure:** Enabling "Show Entropy Minimap" shows no entropy bars, and the 32px child lies past the scrollbar/widget edge and is clipped away — feature is dead/invisible.

### Lower-confidence (depend on orchestrator threading not inspected here)
- `src/intellicrack/ui/app.py:1145-1169` — `_request_tool_confirmation` uses `asyncio.get_event_loop().create_future()` + `QTimer.singleShot(0, show_dialog)`. ### Concurrency note (not a provable Python-level bug)
- Hex editor worker threads (`search`, `statistics`, `scripting`, `signatures`, `strings`, `diff`) call `document.read`/`write_bytes`/`search_*` concurrently with the paint thread's `document.read`. Safe only while PyO3 holds the GIL; if any hexcore method releases the GIL during these operations it becomes a genuine data race. Confirm against the Rust binding's GIL behavior.

## Recommended remediation order
1. **H1–H4** — crashes + unreadable logs.
2. **Thread-safety / freeze cluster** — M1 (stack viewer), M2 (status/refresh timeouts), M3–M5 (VNC + sandbox probe).
3. **Wrong-data cluster** — M6 (Frida device id), M7 (32-bit registers), M9 (float search), M10 (text-search codec), M11 (tool install path).
4. **Systemic refactors** — cross-thread `singleShot`→`pyqtSignal`; theme-aware color resolution + `theme_changed` subscription; blocking bridge calls → async worker with timeout. These three knock out ~20 findings together.
5. Remaining MEDIUM (graph/layout) then LOW (column sizing, splitter collapse, i18n, minor leaks).
